# Platform Deprecation Registry

> Maintained by the Platform Reliability group. Last reviewed: 2026-10-28.

## Purpose

The deprecation registry is the single source of truth for code paths that the
platform team intends to remove. The release tooling reads this document on
every build and refuses to ship when the registry is malformed, when an entry
points at a path that is missing from the module audit, or when the registry
is not cleanly separated from the surrounding prose.

## How entries are written

Each entry occupies one standalone line. The release parser applies the grammar
without leniency: an unticked checkbox, the repository-relative file path, a
colon, the current line number, the closing double asterisk, a space, a hyphen,
a space, and a non-empty one-line description. Nothing may follow the description
on the same line. Blank lines are tolerated between entries, and the section
ends at the next heading of the same level.

## Quarterly review

The platform team refreshes the registry at the start of every quarter. Service
owners confirm the removal window, security signs off on the data-retention
impact, and the release manager publishes the refreshed document to the
integration branch. The audit feed is regenerated by the build farm shortly
before the review.

## Appendix

The registry is mirrored into the build manifest. Any change to this file must
be announced in the release channel before the next scheduled build. Every entry
must remain traceable to an owner and to a target removal window.
